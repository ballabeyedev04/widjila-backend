PARTIE A — DÉPLOIEMENT DU BACKEND (API)
ÉTAPE 1 — PRÉREQUIS ET INFORMATIONS DU SERVEUR
Ce dont vous avez besoin avant de commencer
Serveur Contabo
VPS Cloud 4 vCPU / 8 Go RAM recommandé (le mode cluster et le pool
PostgreSQL sont dimensionnés pour 4 cœurs — voir ecosystem.config.js).
Ubuntu 22.04 ou 24.04 LTS.
Adresse IP publique
Notez l'IP de votre VPS depuis le panel Contabo (ex : 185.12.34.56).
Nom de domaine
Ex : suivie-chantier.com — achetez sur Namecheap, OVH, Gandi, etc. Un seul
domaine suffit : ce projet sert l'admin ET l'API depuis la même origine (voir
étape 7).
Client SSH
Windows : PuTTY ou Windows Terminal. Mac/Linux : terminal intégré.
Code source
Deux dépôts GitHub séparés — un pour le backend, un pour l'admin. Chacun a
son propre pipeline de déploiement continu (étapes 12 et 20).

ÉTAPE 2 — CONNEXION SSH ET MISE À JOUR DU SYSTÈME
2.1 — Se connecter au serveur
Ouvrez un terminal et connectez-vous avec l'adresse IP fournie par Contabo. Remplacez 185.12.34.56 par
votre vraie IP.
# Depuis votre PC (Windows Terminal, Mac, Linux)
ssh root@185.12.34.56
# Entrez le mot de passe reçu par email Contabo
# Vous verrez : root@vps:~#
■  La première connexion demande de confirmer l'empreinte SSH. Tapez “yes” et appuyez sur Entrée.
2.2 — Mettre à jour le système
apt update && apt upgrade -y
# Installer les outils essentiels
apt install -y curl git nano ufw htop unzip

ÉTAPE 8 — LANCER LES CONTENEURS DOCKER
Docker lance trois conteneurs : PostgreSQL, Redis et le backend Node.js — reliés par un réseau Docker
interne, aucun des trois n'expose de port directement sur Internet à part le backend, en loopback uniquement.
8.1 — Premier lancement
cd /var/www/suivie-chantier
docker compose -f docker-compose.prod.yml up -d --build
# 1re fois : 3 à 5 min (téléchargement des images) — ensuite ~30 s
8.2 — Vérifier que les conteneurs tournent
docker compose -f docker-compose.prod.yml ps
# Attendu :
# suivie_chantier_postgres Up (healthy)
# suivie_chantier_redis Up (healthy)
# suivie_chantier_backend Up (healthy)
docker compose -f docker-compose.prod.yml logs -f backend
# Cherchez : "Connexion PostgreSQL établie" et "Serveur lancé sur"
# Quitter les logs : Ctrl+C
8.3 — Tester que l'API répond
curl http://localhost:3000/health
# {"status":"ok","db":"connected","uptime":...}
ÉTAPE 9 — VÉRIFIER MIGRATIONS ET COMPTE ADMIN


--- page 9 ---
✔  Contrairement à un déploiement manuel classique, rien à lancer à la main ici : docker-entrypoint.sh attend la
base puis applique les migrations avant de démarrer le serveur, et le compte super-admin (ADMIN_EMAIL /
ADMIN_PASSWORD du .env) est créé automatiquement par le worker principal au premier démarrage. Une
migration en échec empêche le conteneur de démarrer — le healthcheck de l'étape 8.2 est donc déjà la preuve
que le schéma est à jour.
9.1 — Vérifier quand même (recommandé au premier déploiement)
docker compose -f docker-compose.prod.yml exec backend npx sequelize-cli
db:migrate:status
# Toutes les migrations doivent afficher "up", notamment :
# up 20260809000000-create-remaining-tables-and-indexes.js
# up 20260809000001-create-utilisateur.js
# up 20260809000002-module-extensions.js
■  20260809000000-create-remaining-tables-and-indexes.js crée toutes les tables et index d'après les modèles
Sequelize actuels — idempotente, elle ne modifie jamais une table déjà existante et peut être rejouée sans
risque.
9.2 — Vérifier la connexion admin
Une fois l'admin déployé (Partie B), connectez-vous avec ADMIN_EMAIL / ADMIN_PASSWORD tels que
définis dans le .env à l'étape 6. Activez le MFA depuis le profil dès la première connexion : il est obligatoire
pour accéder aux routes super-admin (/admin/*) de la plateforme.

ÉTAPE 12 — DÉPLOIEMENT CONTINU (CI/CD GITHUB ACTIONS)
Une fois ce paramétrage fait, un simple git push sur main suffit : plus besoin de se reconnecter en SSH pour
chaque mise à jour.
12.1 — Ce que fait le pipeline (déjà dans le dépôt)
Job “test”
npm ci + npm test (suite Jest) — le déploiement ne démarre JAMAIS si un test
échoue.
Job “deploy”
SSH vers le VPS, git pull, docker compose up -d --build backend, attente
“healthy”, contrôle final via /health.
security.yml
npm audit + scan de secrets committés (Gitleaks) à chaque push et pull request.
12.2 — Configurer les secrets GitHub (une seule fois)
Dans le dépôt backend sur GitHub : Settings → Secrets and variables → Actions → New repository secret.
VPS_HOST
IP ou domaine du serveur
VPS_USER
nodeapp
VPS_SSH_KEY
Clé privée SSH de nodeapp (la clé publique correspondante doit être dans
~/.ssh/authorized_keys sur le VPS)
